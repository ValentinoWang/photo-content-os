把 OpenClaw Media 原型接到真引擎上

这份清单把可点击原型上的每一块承诺，对照 photo-content-os 仓库里真实存在的能力，逐条给出判定：能直接接的、要补后端的、必须先拍板的、以及原型本身写错了要改的。每条都标了真实文件路径，不引用文档里的示例路径。

待 SSOT 整改：本页是审核输入，当前整改范围、证据和验收命令以 开发清单审核整改 SSOT 为准。

引擎 ValentinoWang/photo-content-os @ 4da5213 现有前端 99_System_OpenClaw/desktop/（约 1000 行） 原型 OpenClaw Media 可点击原型（9 屏）

先说清楚一件事：现有前端和原型不是同一个东西的两个版本

仓库里已经有一个前端，叫 Photo Content OS Studio（desktop/）。它是一个文档版本化编辑器：8 个标签页把 Brief、脚本、分镜、EDL 全部当作「有稳定 ID 的文本区块」来编辑，核心能力是选中区块改、锁定区块、版本 diff、非破坏性回滚、下游 stale 标记。

原型是另一种东西：一个素材管理 + 时间线工作台。工作台、整理台、素材库这三屏在 Studio 里完全没有对应物；而 Studio 的研究与参考、Brief、脚本、交付、发布与复盘这五块，原型一块都没画。

所以这不是「把旧界面换个皮」，而是两套 IA 的合并。清单最后一节专门列了「不要丢的东西」——那些 Studio 已经做好、原型却没覆盖的能力，换界面时最容易被顺手删掉。

另一条边界来自仓库 README 自己的话：当前稳定交付边界是「经过机器校验的剪辑方案和交接包」，预览粗剪和可编辑时间线是可选本地能力。原型上任何暗示「自动出成片」的表达都越过了这条线。

已拍板的三件事

2026-09-01 拍板。原来的三个待决项都有了结论，判定从「需先拍板」转为「需补后端」，下面每条第一行是拍板结果。

原型承诺「AI 会按拍摄时间和地点分成一个个事件，配好实况照片、认出重复连拍，整理成批等你确认」，并展示了 3 个已分好的批次。
后端现状这个能力完全不存在。全量搜索 scripts/ 没有任何聚类 / 时间分组 / 事件切分逻辑。批次边界 100% 靠人手动建目录 00_Inbox_Mac_Intake/{batch_id}/ 再手填 00_批次说明.md。EXIF 的 GPS 经纬度已经在 manifest 里采集了（gps_latitude / gps_longitude / location_raw，见 01_scan_media_manifest.py），但没有任何代码消费它做分组。
拍板结果做，不做任何降级。整理台保留「AI 自动分事件、分批」的完整承诺。
要做什么新写一个分批器模块：读 media_manifest.json 的拍摄时间与 GPS（字段已采集），按时间间隔 + 地理距离阈值切事件，输出带 JSON Schema 的批次计划（建议 schemas/inbox_batch_plan.schema.json）。批次计划先给用户确认，确认后才交给 34 / 35 建项目和迁移——所以第 08 节 t1（给 35 补测试）必须排在它之前。这是整份清单里工作量最大的单块新增。
原型承诺素材库有「按标签筛选」的一排标签、86 张卡片计数、按分类树浏览、详情栏显示复用标签和适合用途。
后端现状资产卡片是 Markdown 文件（15_register_reusable_asset.py 的 build_card()，模板 templates/02_Asset_资产卡片_TEMPLATE.asset.md），复用索引是一行一条的 Markdown 列表（02_Asset_Library/Reusable_通用素材索引.md）。标签和用途字段确实有（--tags / --uses），但没有 JSON 索引、没有 schema、没有反查、零测试。UI 要筛选就得拿正则从 Markdown 里捞。
拍板结果增加。
要做什么新增 02_Asset_Library/index.json 结构化索引 + schemas/asset_library_index.schema.json，由 15_register_reusable_asset.py 写卡片时同步 upsert（Markdown 卡片继续保留，人读卡片、机器读索引）。给素材库屏提供只读查询接口，连带补 12 / 14 / 15 的测试（第 08 节 t2）。
原型承诺设置里转写方式默认显示「本机 FunASR」，项目屏的证据来源写着「逐字转写 · 本机 FunASR」。
后端现状03_transcribe_audio.py 的 build_provider() 恰好三种：sidecar（读旁挂 srt/json/txt）、openai_api（要 OPENAI_API_KEY）、pending（只写占位、不假装听过）。没有本地 Whisper，也没有 FunASR，而且默认兜底就是 pending——开箱即用状态下转写是空的。
拍板结果默认以阿里云线上模型 API 为主；Codex 订阅额度不覆盖音频转写，FunASR 作为本机兜底方案保留。
Codex 额度为什么不行：Codex 登录使用的 ChatGPT 订阅额度只覆盖 Codex 代理本身的文本与代码模型调用，订阅侧没有音频转写端点。OpenAI 的转写能力走 API 平台按量计费，需要单独的 OPENAI_API_KEY；Codex 可以编排流程，但不能替代音频转写提供方。
要做什么① 在 03_transcribe_audio.py 的 build_provider() 中新增 dashscope 并设为默认：读取 DASHSCOPE_API_KEY，调用阿里云录音文件转写并输出符合 schemas/audio_transcript.schema.json 的结果。② 新增 funasr 本机 provider 作兜底，输出字级时间戳。③ 保留现有 sidecar、openai_api 与 pending。④ 设置页默认显示「阿里云在线转写」，如实提示在线转写会将音频发送给阿里云。

接界面之前该还的债

这些不是原型引入的新需求，是现有代码的窟窿。UI 一接上去，这些窟窿就会变成线上问题。
